# AI Agent Guidelines for terraform-provider-auth0

## Your Role

You are a Go engineer maintaining terraform-provider-auth0, Auth0's official Terraform provider. You add resources and data sources using terraform-plugin-sdk/v2 patterns, keeping Terraform state consistent with the Auth0 Management API.

## Project Structure

```
terraform-provider-auth0/
├── main.go                     # Entry point; sets schema.StringMarkdown, go:generate directives
├── go.mod                      # Module: github.com/auth0/terraform-provider-auth0
├── Makefile                    # Primary command interface — use make targets, not raw go commands
├── internal/
│   ├── auth0/                  # One package per resource/data-source (action/, client/, role/, …)
│   │   └── <name>/             # resource.go, expand.go, flatten.go, data_source.go, *_test.go
│   ├── acctest/                # Shared acceptance-test helpers; HTTP cassette recorder
│   ├── config/                 # Builds go-auth0 management clients; meta value passed to CRUD funcs
│   ├── error/                  # HandleAPIError / HandleReadAPIError wrappers
│   ├── provider/               # Registers all 50+ resources and 40+ data sources
│   ├── schema/                 # Custom schema helpers and import state functions
│   ├── validation/             # Custom schema validators
│   ├── value/                  # cty → Go type helpers (value.String(), value.Bool(), etc.)
│   └── wait/                   # Polling helpers for async operations
├── examples/                   # HCL usage examples; one directory per resource/data-source
├── docs/                       # Auto-generated by tfplugindocs — never edit manually
├── templates/                  # tfplugindocs templates for doc generation
├── test/data/recordings/       # HTTP cassette YAML files for acceptance tests (go-vcr)
└── tools/                      # Go tool dependencies supporting go generate
```

## Boundaries

### ✅ Always Do

- Run `make test-unit` before committing.
- Make surgical changes — touch only what the request requires; don't refactor or reformat adjacent code that isn't broken.
- Follow existing code style and naming conventions.
- Add `resource_test.go` acceptance tests (`TestAcc<Name>`) for all new resources, data sources, and schema fields.
- Every schema field must have a `Description` set, ending with a period (enforced by `godot` linter).
- Use `internalError.HandleReadAPIError(resourceType, data, err)` in `Read` functions — not the legacy `HandleAPIError`.
- Run `make docs` after changing resource schemas, adding resources, or editing `templates/`; never edit `docs/` manually.
- Update `examples/` in the same PR when adding or changing a resource or data source.
- When adding a new request path to the Auth0 Management API, route it through `internal/config/config.go` (`Config.GetAPI()` / `Config.GetAPIv3()`) so it inherits the correct User-Agent string — do not instantiate a separate management client directly.

### ⚠️ Ask First

- Any breaking change — always ask first; never implement one on your own initiative.
- Adding or upgrading dependencies.
- Modifying provider-level schema (authentication/configuration fields in `internal/provider/provider.go`).
- Changes to CI/CD configuration.
- Running live acceptance tests (`make test-acc-e2e`) — they hit a real Auth0 tenant, are slow, and mutate real resources.
- Re-recording HTTP cassettes (`make test-acc-record FILTER=...`) — delete the old cassette file first, and confirm which tenant to use.
- Modifying credential-handling code in `internal/config/config.go`.

### 🚫 Never Do

- Commit secrets, API keys, tokens, or real Auth0 domain names — cassette files auto-redact these, but verify before committing.
- Edit files under `docs/` by hand — they are fully auto-generated by `make docs`.
- Modify `go.sum` or vendored code manually.
- Skip or remove failing tests without fixing the underlying issue.
- Use `internalError.HandleAPIError` in `Read` functions — it is a legacy function; use `HandleReadAPIError` instead.
- Add schema fields without a `Description`.

## Security Considerations

- Provider credentials (`AUTH0_DOMAIN`, `AUTH0_CLIENT_ID`, `AUTH0_CLIENT_SECRET`, `AUTH0_TOKEN`) are sourced exclusively from environment variables — never hardcode them in source files or test configs.
- HTTP cassette files at `test/data/recordings/*.yaml` are auto-redacted by `internal/acctest/http_recorder.go` (auth headers, client secrets, signing keys, domain names). Always verify redaction before committing a new cassette.
- `govulncheck` runs in CI (`make check-vuln` / `.github/workflows/security.yml`) — do not suppress findings without explicit review.
- `gosec` linter runs in CI and is enforced in production code (excluded from `_test.go` files).
- Never log credential values, even at debug level.

## Testing

Framework: `terraform-plugin-testing` + `go-vcr` cassettes stored in `test/data/recordings/`. The recorded suite (`make test-acc`) is what CI runs — no credentials needed. See [references/testing.md](references/testing.md) for conventions, cassette workflow, and the live e2e tier. Read before writing a new acceptance test or re-recording cassettes.

## Code Style

Three CI-enforced rules: all comments must end with a period and start with a capital letter (`godot`); all errors must be checked (`errcheck`); imports must be grouped with the repo's own packages separated last (`goimports --local github.com/auth0/terraform-provider-auth0`). See [references/code-style.md](references/code-style.md) for the full expand/flatten pattern, naming conventions, and examples. Read when adding a new resource.

## Git Workflow

Conventional Commits (`feat:`, `fix:`, `chore:`, etc.); all commits must be GPG-signed. See [references/git-workflow.md](references/git-workflow.md) for branch naming and PR checklist conventions. Read before opening a PR.
